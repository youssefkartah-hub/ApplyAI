01The rules

Out, around and back, with nobody touching the robot

  • Out and backFollow 1.5 m of black tape with a gentle S-bend to a wall, turn around, and return to the start bar.
  • No turn commandThe library's drivetrain.turn() is banned. A team whose code calls it loses the race.
  • Hands offBoth robots start on one button press. After that the program is on its own, with one restart if it leaves the track.
  • Head to headTwo identical lanes, 40 cm apart. The first robot back across the finish bar wins.

02Hardware

What the program has to work with

The robot is an XRP kit. We did not design the chassis or the electronics; the work was the program and its tuning.

  1. 1Ultrasonic rangefinder. Measures the distance to the wall at the end of the lane.
  2. 2Control board. Runs the MicroPython program, drives the motors, and carries the gyro used to measure the turn.
  3. 3Two drive wheels. Steering is the difference between the left and right motor effort.
  4. 4Two ball casters. They carry the front and let it swing freely.
  5. 5Battery lead. Power from the battery pack plugs in here.

Out of sight under the chassis: two reflectance sensors, one each side of the tape. Each reads 0 over white and 1 over black.

03Control law

One number to steer by

Subtract the right sensor from the left and you get an error, e = L − R. Positive means the tape is to the left, zero means centered. The controller's whole job is to drive that number to zero. We built it up one term at a time, and each term fixed something I could see the last one get wrong.

  • 1 · Bang-bang

    u = ±0.15

    Steer by a fixed amount toward the tape. It always overshoots, so the robot weaves, and the weave grows with speed.

  • 2 · Proportional

    u = Kp e

    The two sensors together say how far off the robot is, not just which side. A small drift gets a small correction.

  • 3 · Proportional + integral

    u = Kp e + Ki ∫e dt

    Adds up the leftover error, so a steady pull to one side gets cancelled instead of tolerated.

How we tuned it

  • Change one number between runs, and start from the same spot every time. Otherwise there is no telling which change did what.
  • Raise the gain until the robot starts to oscillate, then back off by 30 to 50 percent.
  • Tune again whenever the base speed changes. The gain that is smooth at one speed oscillates at a higher one.

04Architecture

Four states to run the race

  1. 01OUTBOUND

    On every pass of the loop: read both line sensors, compute the error, set the two motor efforts, and check the rangefinder.

    Exit whenthe rangefinder reads 15 cm or less several times in a row.

  2. 02TURN

    Reset the gyro yaw and spin in place. Slow down early, then creep until a line sensor sees tape.

    Exit whena sensor finds tape, after about 150° of rotation.

  3. 03RETURN

    The same controller with the rangefinder ignored. The bend now curves the other way.

    Exit whenboth sensors read black at once: the finish bar.

  4. 04DONE

    Motors off, LED green. In a race the clock stops when the first robot crosses the bar.

05Decision

Turning 180° without the turn command

The line sensors say nothing while the robot rotates, so the program has to know by some other means when it has turned far enough. It also keeps rotating after the motors are cut: the robot coasts 15 to 20 degrees.

What tells the robot the turn is finished? Options

Gyro alone

  • Counts degrees from the moment the turn starts.
  • Drifts after a couple of seconds.
  • The coast after the motors stop lands it off the line.

Gyro, then the tape Chosen

  • Spin fast on the gyro and slow down before 180°.
  • Creep until a line sensor finds the tape, the best reference for the last few degrees.
  • The tape the robot just left looks the same as the way home.

How the last problem is handled: the program ignores the line sensors until the gyro shows about 150° of rotation, so the line the robot just left is never mistaken for the return path.

06Failure handling

Two ways it could fail, and what the program does about each

One bad reading

The rangefinder returns 65535 when it sees nothing, and it can catch a glimpse of the neighboring lane's wall. A single false reading would start the turn in the middle of the track.

A real wall keeps being there and a glitch does not, so the program requires several readings in a row at 15 cm or less before it leaves the outbound state. Nobody may touch a robot after the start, so a false turn would cost the team's one restart.

A robot that pulls to one side

If one motor is slightly weaker, a proportional controller settles beside the line. It needs a leftover error to produce the correction that cancels the pull. More gain shrinks that offset but never removes it, and too much gain brings the oscillation back.

The integral term adds up the leftover error until the correction holds on its own. It is clamped so it cannot wind up, and it is reset whenever the state changes.

07What I took from it

Four things a 1.5 m line taught me

  1. Earn each term.Bang-bang first, then proportional, then integral. Each step fixes one thing I could see the last one get wrong.
  2. Every sensor fails in its own way.The gyro drifts, the rangefinder glitches, the line sensors go blind in a turn. The program is mostly about which one to trust when.
  3. A gain is only right at one speed.The setting that is smooth at one base speed oscillates at a higher one. Faster means tuning again.
  4. The demo is the test.Code that runs on the bench and code that survives a start with hands off are two different things.
